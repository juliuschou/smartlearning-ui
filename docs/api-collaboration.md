# 前後端 API 協作流程

## 目的與範圍

這份文件說明前端與後端如何一起確認、記錄、實作及驗收 API 的新增與變更。流程以人工討論和審查為主；目前不包含自動產生 API 說明、程式碼或同步工作的工具。

本專案前端已有共用 API 呼叫工具，但目前沒有在這個倉庫找到已確認的後端 API 說明或功能端點。因此，以下流程是協作約定的建議；實際負責人、規格存放位置和版本編號方式，請由團隊確認後採用。

## 分工原則

- **前端**說明使用情境、需要的資料與畫面行為，依雙方確認的 API 說明接入功能，並回報實際整合時遇到的差異。
- **後端**說明 API 實際提供的行為、輸入限制、回覆內容、錯誤情況及權限要求，並在行為改變時更新 API 說明。
- **前後端一起**確認 API 說明、相容性、測試方式及上線順序。誰負責維護原始 API 說明、誰負責審查，應在團隊內明確指定。

API 說明應有一個雙方都找得到的權威版本。若說明存放在後端專案或其他位置，前端的改動紀錄應連回該版本，不要在不同地方各自維護互相矛盾的副本。

## 簡短範例：新增課程清單 API

以下只是協作格式示例，`GET /courses` 和欄位內容是假設情境，不代表本專案已有此 API 或已確認這份契約。

| 項目 | 範例內容 |
| --- | --- |
| 目的 | 前端需要顯示可選課程清單。 |
| API | `GET /courses`；需不需要登入由前後端確認。 |
| 成功回覆 | `data` 為課程清單，例如 `[{"id":"c1","name":"自然科學"}]`；完整回覆仍須符合共同確認的格式。 |
| 錯誤情況 | 例如沒有權限時，約定錯誤代碼及畫面要顯示的處理方式。 |
| 相容性 | 新增清單不影響既有 API；若回覆欄位有變，先確認是否會影響已使用該欄位的畫面。 |
| 版本與紀錄 | 在 API 說明中記下這次變更及對應的後端改動；版本編號方式由團隊確認。 |
| 驗收 | 後端提供成功及錯誤範例；前端確認清單顯示與錯誤提示，並記下測試結果。 |

## 一次 API 變更的合作步驟

### 1. 提出需求

提出方先交代要完成的使用情境、預期結果及需要處理的失敗情況。前端提出需求時，描述畫面需要什麼；後端提出變更時，說明原因及受影響的使用方式。

### 2. 動手前先確認 API 說明

前後端一起確認下列事項，並把結論寫在權威 API 說明或可追蹤的改動紀錄中：

- API 的用途、網址和操作方式。
- 是否需要登入、使用者權限或其他憑證。
- 要送出的資料：欄位型態、是否必填、允許的值及範例。
- 成功時會收到的資料、回覆狀態及範例。
- 可能的錯誤：錯誤代碼、代表的情況、是否可重試，以及前端應如何處理。
- 是否牽涉 Cookie、跨站請求保護、重複送出防護或其他特殊標頭。
- 這次變更是否會讓既有呼叫方式失效；若會，如何切換及何時停止支援舊方式。

若有尚未決定的內容，明確標為待確認，不要讓前端或後端各自猜測。

### 3. 記錄版本與變更內容

每次 API 說明變更都要能對應到相關的後端改動，並記下：

- 變更日期或改動識別資訊。
- 改了什麼、為什麼改，以及會影響哪些使用者或畫面。
- 是否仍相容舊用法；不相容時的過渡方式和預計停止支援時間。
- 前端及後端的負責確認者、測試方式和未完成事項。

版本號採用哪種格式由前後端共同選定；目前不要假設本專案已有固定版本規則。若後端另有正式版本號，變更紀錄應沿用並附上可查閱的位置。

### 4. 前後端各自實作並互相交接

- 後端依確認過的說明實作，並提供可供前端核對的實際回覆範例或測試環境資訊。
- 前端依同一份說明更新呼叫資料、資料型別及使用 API 的畫面。
- 前端沿用 `lib/api/client.ts` 的共用呼叫工具處理一般 HTTP 請求，不要在各畫面重複處理共通的請求與錯誤封裝。
- 若實際回覆和說明不同，先記錄差異並請雙方決定要修正實作還是更新說明；不要只在其中一端默默補例外。

### 5. 一起驗收

- **後端確認**：實際回覆符合已確認的 API 說明，成功和失敗情況都符合約定。
- **前端確認**：呼叫成功時畫面能使用回覆資料；錯誤時有合適的處理；需要登入或特殊標頭的情況符合約定。
- **雙方確認**：對照實際請求與回覆範例，確認狀態、資料格式和錯誤處理一致；記錄測試結果及尚未解決的問題。

前端共用 API 呼叫工具的測試可參考 `test/api-client.test.ts`。它驗證共用回覆格式、錯誤處理和請求行為；新增或變更功能時，仍應為該功能補上適合的測試。是否執行連接真實後端的測試，需確認後端測試環境已準備好，並遵循該環境的使用規則。

### 6. 合併與通知

前後端各自完成審查和驗收後再合併。改動說明至少要讓接手者知道：API 說明在哪裡、改了什麼、前端是否需要配合、是否有舊用法即將停止，以及如何確認功能正常。

## 不相容變更的處理

如果欄位、網址、權限或回覆方式的改變會讓既有畫面無法使用：

1. 在實作前標明這是不相容變更及受影響的使用方式。
2. 前後端先確認更新順序，避免後端先移除舊方式而前端尚未更新。
3. 約定過渡方式與停止支援舊方式的時間；若無法同時保留新舊方式，要協調同一個上線時段。
4. 前端更新並驗收後，由後端確認何時可以停止支援舊方式，並在變更紀錄中註明結果。

## 本專案前端現況參考

以下是目前前端程式的實作情況，可作為協商 API 說明時的參考；除非前後端已確認，不能只因前端如此實作，就視為後端已承諾相同規格。

- `lib/api/client.ts` 集中處理 HTTP 請求、登入 Cookie、變更資料時的 CSRF 標頭、錯誤整理及回覆資料拆封。
- `lib/api/types.ts` 定義前端目前使用的成功／錯誤回覆格式，包含 `data`、`error`、`meta.schemaVersion`、`meta.requestId` 等欄位。
- `test/api-client.test.ts` 是共用請求工具的測試範例，不代表每個功能 API 都已經有測試。

如需調整共用請求工具的行為，應另外確認對其他 API 呼叫的影響；單一功能的資料欄位變動通常應在該功能的型別與呼叫處理，不要因此不必要地改動共用工具。

## 本次範圍不包含

本文件只整理人工協作流程，不新增 API 自動產生、型別同步、程式碼產生、CI 檢查或其他自動化。若團隊日後希望採用這些做法，應另行確認需求、工具及維護責任。
